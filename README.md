# discord-secretary-bot

内輪の1サーバー向けの管理者Discord Botです。設計は「管理者Discord Bot 設計書」と「詳細仕様」にあります。

現在は **Phase 3**(イベントルール)まで実装しています。

- **対話モード**: Botをメンションすると、そのチャンネル(スレッドは別扱い)で会話が始まります。メンションやBotへの返信には必ず答え、それ以外の発言は宛先判定モデルで「Bot宛てか」を判定して答えます。自分宛ての発言が5分途切れると眠ります。
- **`/llm`**: 本人にだけ見えるパネルで、APIキー(Claude API / TypeSafe / GLM Coding Plan)と、応答に使うモデル・宛先判定に使うモデル(TypeSafeのJevは宛先判定専用)を設定します。どちらのモデルも必須で、自動では選びません。設定が終わっていない人の発言は無視し、メンションされたときだけ設定を促すDMを会話ごとに1回送ります。
- **読み取りの制限**: Botは管理者権限で何でも読めるため、応答に使える情報を「話し手が読めて、かつ今のチャンネルを見られる全員が読めるチャンネル」に決定的に絞ります。読める経路は許可リスト方式で、それ以外は拒否します。
- **ツール**: 履歴の取得(1応答あたり最大500件)、サーバー内メッセージ検索、チャンネル一覧、メンバー検索、読み取り専用サンドボックス(QuickJS/WASM)でのコード実行。Web検索とページの読み取りも使えます。使うサービスは各自が `/llm` で選びます(Claudeのサーバー側ツール、GLM Coding PlanのWeb Search / Web Reader、Tavily、使わない。既定は応答モデルの標準)。Tavilyのキーも各自 `/llm` で登録します。`WEB_SEARCH=off` で全員分を無効にできます。
- **書き込み(Phase 2)**: 投稿、チャンネル・ロール・権限上書きの作成/変更/削除、ロール付与、タイムアウト、キック、BAN、DMなどは、エージェントが `propose_plan` で変更案(Plan)を出し、Botが発言への返信として承認ダイアログを出します。
  - ダイアログは操作名・対象・変更前→変更後・危険度をPlanから決定的に描画し、AIの説明文は載せません。同じ操作を複数の対象にするときは1行にまとめ、危険度で枠の色が変わります。「実行」を押せるのは依頼者だけで、期限は5分です。
  - 戻せる操作はボタン1回で実行します。戻せない操作(メッセージ削除、キック、チャンネル・ロール削除、発言削除つきBAN、DM)を含むときだけ、対象の名前(複数なら件数)の入力を求めます。
  - 変更案は基本的にステップの一覧で出します。対象が多いときや条件で対象を選ぶときだけ、エージェントは読み取り専用サンドボックスで動くコードで案を作ります。そのときダイアログはコードと、会話を見ていない別のAIがコード(コメントを除く)だけを読んで書いた説明を最初に見せ、「結果を見る」でステップの一覧とJSONに切り替えられます。
  - 「修正」で直したいことを書くと、エージェントが案を作り直して同じダイアログを置き換えます。期限切れや中止のあとは「出し直す」で、今の状態から確かめ直した案を出せます。実行中は進み具合を表示します。
  - 操作は `src/plan/catalog.ts` の権限対応表にあるものだけで、本文はスキーマで検証し、表にない操作やフィールドは拒否します。依頼者とBotの両方に必要な権限があり、ロール階層でも上にいることを確かめます。
  - 実行直前に対象の状態と権限をRESTで取り直して再検証し、変わっていれば中止します。Discordの監査ログには依頼者を理由として残します。
  - 途中で失敗したら自動では戻さず、「再開」「復元」(済んだ変更を戻す変更案を出す)「そのまま」を選べます。変更前の状態はスナップショットとして90日保存します。DMは1つの変更につき50件まで、1秒以上の間隔で送ります。

- **イベントルール(Phase 3)**: 「#自己紹介 に投稿した人に @メンバー を付けて」のように、決まったことが起きるたびに自動でしてほしいことを会話で頼むと、エージェントが変更案(`propose_plan`)にルールを入れて出します。専用の作成コマンドはありません。
  - 仕組みに必要な変更とルールは1つの変更案にまとまり、承認は1回です。例: 「「vc作成」ボイスチャンネルに入ったら📞付きのボイスチャンネルを作って移動し、空になったら消す」なら、「vc作成」を作るステップと、そのIDを `params` で受け取るルール2つが1つのダイアログに出ます。「実行」でステップが済んだあとにルールが登録され、ステップの結果(`$ref`)は実際のIDに置き換わります。code で作るときは `rule({...})` を `plan(steps, rules)` で返します。
  - ルールは「きっかけ(Gatewayイベント)・許す操作(allow)・コード」の組です。コードはイベントごとに読み取り専用サンドボックスで動き(1回10秒・`discord.get` 50回まで)、変更のステップを返します。
  - ルールは提案の時点でドライランします(このチャンネルの直近のメッセージや依頼者のメンバー情報、なければAIが用意した例のイベントで)。同じ変更案で作るものの値を使うルールは、コードがエラーにならないことだけを確かめます。ダイアログにはきっかけ・許す操作・params・ドライランの結果、「コードを見る」でコードと別のAIがコードだけから書いた説明を、ルールの定義から決定的に描画します。
  - 許す操作には、パスパラメータと本文のほかに、対象の実行直前の状態の条件(`target`、例: 名前が📞で始まるチャンネルだけ削除できる)を JSON Schema で付けられます。
  - ルールのコードは `discord.get(\`/guilds/${guild}/voice-states\`)` でボイスチャンネルの在室者を読めます。`VOICE_STATE_UPDATE` のイベントには直前にいたチャンネル(`before_channel_id`)が付きます。
  - 発火時は人の確認を挟みません。実行器が、すべてのステップが allow のどれかに合うこと(前のステップの値も実行時に照合)、スキーマに合うこと、作成者とBotが今その権限を持つことを確かめてから、Planと同じ経路で実行します。作成者が見られないチャンネルのイベントでは動きません。
  - 安全装置: Bot自身が起こしたイベントでは既定で動かない(直近15秒にBotが変えた対象のイベントも含む)、ルールごとに1分10回まで、3回続けて失敗したら自動で止めて作成者にDM、全ルールの緊急停止。作成者がサーバーを抜けるとその人のルールは自動で止まります。
  - 直すときは会話で「ルール〈ID〉を〜に直して」と頼みます。確認のあと新しい版になります。
- **`/rules`**: 本人にだけ見える管理パネルです。ルールの一覧と詳細(許す操作・コード・最近の実行)、有効化・停止・削除・ドライラン、変更の履歴、監査ログ、全ルールの緊急停止。自分のルールは本人が操作し、他人のルールの閲覧と監査ログの全件は監査ログ表示の権限、他人のルールの停止はサーバー管理の権限とそのルールが使う権限すべて、緊急停止はサーバー管理の権限が必要です。

## 必要なもの

- Node.js 24 以降(22.18 以降でも動きます。TypeScriptは型除去でそのまま実行します)
- Discord Developer Portal で作ったアプリケーション
  - Bot の **Privileged Gateway Intents** で `SERVER MEMBERS INTENT` と `MESSAGE CONTENT INTENT` を有効にする
  - `bot` と `applications.commands` のスコープ、Administrator 権限でサーバーに招待する
- Interactions Endpoint URL は設定しません。すべて Gateway(WebSocket)で受けるので、HTTPポートは開けません。

## 設定

`.env.example` を参考に環境変数を設定します。

| 変数 | 内容 |
|---|---|
| `DISCORD_TOKEN` | Botトークン |
| `DISCORD_APPLICATION_ID` | アプリケーションID |
| `DISCORD_GUILD_IDS` | 任意。使うサーバーのIDをカンマ区切りで。空なら招待されたすべてのサーバーで動きます。会話・権限・読み取りはサーバーごとに分かれ、`/llm` の設定は人ごとに全サーバー共通です |
| `MASTER_KEY` | APIキーの暗号化に使う32バイトの鍵(`openssl rand -base64 32`)。失うと登録済みのキーは復号できません |
| `DB_PATH` | SQLiteのパス(既定 `data/bot.db`) |
| `WEB_SEARCH` | `off` で全員のWebツールを無効にする |

## 実行

```sh
npm ci
npm start
```

起動時にギルドコマンドを一括で上書き登録します(定義が変わっていなければ省略)。停止時にコマンドは消しません。

## 本番と開発

1台のサーバーで本番(prod)と開発(dev)を分けて動かします。それぞれ別のclone、`.env`(Botトークン)、データベース、systemdユニット(`discord-secretary-bot@prod` / `discord-secretary-bot@dev`)を持ちます。操作は `deploy/botctl` で、Discordには何も出しません。

```sh
botctl status              # 各環境で動いているコミット
botctl dev [branch]        # devをブランチの最新にしてテストし、再起動(既定はmain)
botctl promote             # devで動いているコミットを本番へ
botctl rollback            # 本番を一つ前のコミットへ
botctl logs prod|dev [n]   # ログ
botctl install             # 初回の設置(~/discord-secretary-bot/{prod,dev,state})
```

本番に上げられるのは、devで動いているコミットだけです。本番を変える前にはデータベースを `prod/data/backups` に写します。新しいコミットが起動しなければ、元のコミットとそのデータベースに自動で戻します。
